# FSH Codegen Stack

First, while working locally, repositories pull editable paths for their siblings. In CI, they pull from codeartifact. That split is behind a lot of the surprises.

The example app, the template app, and the sales pipeline (an in progress implementation) all have `_generated` repositories in the `be/` and a copious number of other autogenned files in `fe`, `render`, and `opa`. These files are autogenerated from the tooling in `codegen` and `codegen-targets`.

`codegen` emits a CLI that is used to actually perform the autogeneration. It is best to rely on the just files in the repository as opposed to constructing standalone codegen commands.

`codegen-targets` configure `codegen` for the specific environment.

Always edit the templates and not the outputs, and then regenerate.

## Dependency issues

These are the most common time-sinks. Both look like "the package is broken"; neither is.

**A. `Failed to spawn: pytest / uvicorn / pgq` after a repo move.**
The fsh repos moved `~/workspace/fsh/migration/` → `~/workspace/fsh/fsh/` (2026-06-10).
Pre-move `.venv`s have entry-point shebangs hard-coded to the old path; uv won't
rewrite them on `sync` if the venv looks healthy. Any sibling repo with a pre-move
venv hits this on its first spawn.

```bash
head -1 .venv/bin/pytest          # if it points at .../migration/... it's stale
rm -rf .venv && uv sync --group dev --group lint
# codegen-targets workspace root: uv sync --all-packages --group dev --group lint
```

**B. `SyntaxError: multiple exception types must be parenthesized` (or other
Py2-looking syntax) on import.** The PyPI wheels are clean — corruption lives in
uv's _unpacked_ cache `~/.cache/uv/archive-v0/` (~5GB), hardlinked into venvs.
`uv cache clean` / `--refresh` / `--reinstall` do **not** purge it.

```bash
rm -rf ~/.cache/uv/archive-v0     # safe: existing venvs keep their hardlinked data
rm -rf <pkg>/.venv
cd <pkg> && uv sync --all-groups  # re-unpacks fresh from clean wheels
```

Verify by compiling, not grepping (`except A, B` appears legitimately in docstrings):

```bash
python -c "import pathlib,py_compile; [py_compile.compile(str(f),doraise=True) for f in pathlib.Path('.venv/lib/python3.13/site-packages').rglob('*.py')]"
```

Pre-existing, unrelated red on `codegen-targets` `main`:
`test_be_root.py::test_psycopg_flag_adds_dep` and `test_rate_limit_flag_pulls_in_psycopg`.
Run be tests with `PYTHONPATH=.`.

## Permissions / authz stack

Spans three sources:

- `python-lib/src/fsh_lib/opa.py` — client + support-graph DNF translator (the
  presence/`_presence_dnf` walker).
- `codegen-targets/.../codegen-be/.../templates/init/opa_setup.py.j2` → renders
  `be/_generated/opa_gate.py`.
- `codegen-targets/.../codegen-opa/.../templates/` — entrypoint + rbac.rego +
  generated `entrypoint_test.rego`. Role/binding loaders + sample `role_bindings`
  scaffold live in `codegen-be-root` templates.

Regenerate with `just gen` in the consumer's `be/` and `opa/` dirs.

**Semantics (settled June 2026, strictly fail-closed):** no bindings → deny;
OPA unreachable or no bundle → deny (`fail_open=False` default); a custom rule
file takes routing precedence.

**Router capture is per-_rule_, not per-package** (changed 2026-06-12): a layer
file captures `allow`/`deny` independently, and only if it _defines_ that rule
(`!= null` presence gates in `entrypoint.rego.j2` — deliberately not
`object.keys`, which would drag `deny` bodies into the `allow` compile graph).
Delete `allow` from a rule file → it falls through resource-root → global-root →
RBAC, and `default allow := false` keeps it closed.

**COUPLING:** the per-rule entrypoint requires the fsh-lib support-walker
presence handling (`_presence_dnf` + constant-folding negated support refs) or
list endpoints with captured layers raise `OpaError`. **Ship fsh-lib before
regenerating consumer entrypoints.** Presence resolution needs rule files to keep
their `default` lines (the walker refuses presence checks on default-less rules).

`<resource>:view` covers both get point-checks and list filtering (the filter
partially evaluates the same `allow`). Demo bindings (`be/seed.py`):
alice=admin+member, bob=member, carol=none. Loaders use
`selectinload(User.role_bindings)` with `lazy="raise"`. Dev OPA: `opa run
--server --watch` (hot-reloads).

**Build the bundle PLAIN, never `-O 1/-O 2`.** The routing entrypoint's dynamic
ref `data.<pkg>.rule[res][act]` is an indexed lookup when plain; partial eval
expands it into a quadratic resource×action cross-product (~6× slower/decision,
and 2/15 unit tests fail because `with data.<pkg>.rule as ...` mocks stop
routing). Keep `--ignore '*_test.rego'`; gate the image with `opa test` +
`opa eval --fail` replays. (Old template comments claimed the opposite — don't
trust them.)

## The publish / release chain (CI red ≠ your bug)

Each layer's CI is red until the layer **below it is _published_** (release-please
`chore(<pkg>): release X` PR merged), not merely merged to main. Local dev hides
this because editable siblings satisfy the floor.

**x-action stamp** (`codegen-be/operations/action.py` →
`fsh_lib.openapi.construct_openapi_extra` / `X_ACTION`) is **new in fsh-lib
0.9.13** (absent in 0.9.12). Without it the FE catalog misclassifies a `bulk: true`
action as `collection` and the hand-owned `src/actions/.../*.tsx` fails `tsc`.
So `codegen-be`/`be-root` must pin `fsh-lib>=0.9.13` (a bare `fsh-lib` lets CI
resolve 0.9.12 → `zuban: Module "fsh_lib.openapi" has no attribute "X_ACTION"`).

Full chain to green example-app `fe` (June 2026): publish (1) codegen-be 0.9.13 +
codegen-fe 0.9.7, then (2) `@fsh/components-library` 0.5.0 (the new codegen-fe
emits `defineFields`, `Card title/subtitle`, `Tabs items`, `FSHTableView` props
that 0.4.0 lacks), then bump example-app fe `@fsh/components-library` `^0.4.0`→
`^0.5.0` + refresh `yarn.lock`.

**react-router pin:** `codegen-example-app/fe/package.json` must pin
`@tanstack/react-router` to the **same** version `@fsh/components-library` is
built against (currently `1.170.15`). A mismatch (it was stuck at `1.95.0`)
changes `Route`/`AnyRoute` generic arity → typed `to:` collapses to `never` →
dozens of TS2322/TS2345 router errors even though generation + lint pass. Fix:
bump the app's pin whenever components-library bumps react-router.

## codegen-example-app dev gotchas

This applies to any app generated in this way.

**Judge perf on `yarn preview`, not `yarn dev`.** Runtime is healthy (zero >50ms
long tasks, soft navs ~120ms, BE search 18–120ms). All perceived lag is dev-mode
page load: cold `yarn dev` = 246 module requests / 7.7MB / ~4.5s DCL
(`src/index.css` transform alone 3.4s) vs `yarn preview` prod = 7 requests /
264KB / 180ms. Cause: the editable-mode vite alias serves the components-library
_source_ barrel (no prebundle).

**Dev login:** vite must be on port **5173** (BE CORS default only allows that
origin); creds `alice` / `wonderland` (`be/seed.py`). `useFSHForm`'s
beforeunload dirty-guard fires on the _login_ form after a failed submit and
blocks reloads with a "Leave site?" dialog (froze Playwright). Dev also fills the
250-entry resource-timing buffer — `performance.clearResourceTimings()` before
measuring.

**Async reports serve stale code until you restart the worker.** A _sync_ report
runs in the uvicorn `--reload` web process (auto-picks up regenerated
`_generated/reports.py`); an _async_ report runs in the separate pgqueuer worker
(`just be queue worker` → `uv run pgq run tracker.queue.main:main`), which does
**not** reload. After a regen, sync shows new output, async shows old.
`fuser -k <port>` and `pkill -f "queue worker"` do **not** kill it (it holds no
TCP port; real process name is `pgq run ...`, the `queue worker` match is just
the `just` wrapper). Orphaned `pgq run` procs from a previous `just dev` keep
draining the same queue and can grab a fresh stack's job.

```bash
pkill -f "pgq run"
pgrep -af "pgq run"    # expect exactly one tree after restart
```

**X-Invalidate-Queries silently no-ops cross-origin** unless BE CORS sets
`expose_headers=["X-Invalidate-Queries"]`. Server-driven cache invalidation (FE
`api/invalidation.ts` reads the header → `queryClient.invalidateQueries`) gets
`null` because browsers hide custom _response_ headers from JS even with
`allow_headers=["*"]` (that only governs the request side). Masked by most CRUD
(forms `window.history.back()` → list remounts and refetches); surfaced by
saved-views (same-page tab strip expects a refresh). Fixed in
example-app/be/main.py (2026-06-17); the `be_root` `main.py.j2` template likely
still ships the gap — fix it there for every generated app.

## justfiles and merges

The just files are insanely useful

You should largely not be running any commands directly and instead relying on what's in the just files.

We use just-pm (just-package-manager) to sync packages.  You can invoke this by running just-pm sync.  Many justfiles have just sync bound to this.

Things like relinearizing database migrations, putting a database up, managing it, can all be done via just.  Putting up the dev servers can be done with just d.  just d <offset> allows you to create a new stack in a place that doesn't conflict.
